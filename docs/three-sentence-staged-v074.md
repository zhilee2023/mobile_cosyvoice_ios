# v0.7.4 / build18：三句共享一次 Flow

## 依据

v0.7.3 的 iPhone 三句测试完成且未触发内存保护。两句分阶段在三句默认文案上
仍需两次 LLM 准备和两次 Flow 创建。两次测试的计算 RTF 分别为 1.744 和
1.668，首句首块入队约 6.5 秒，峰值约 1.61 GB。LLM 保留路线完成三句，
计算 RTF 1.756，首块约 5.48 秒，峰值约 2.16 GB。随机采样的音频长度不等，
这些数值不能证明某路线更快。

## 新对照

- 最多取三个完整句段；逐句清 KV 并生成正常 EOS 的 speech token。
  每句仍限 105 token，错误时不截断，按既有有限拆句重做整批。
- 完成准备后销毁 LLM，等待至少 2500 MB 可用内存；再创建一次 CPU High
  Flow384，运行两步，逐句复用同一会话。HiFT Low 逐句运行和播放。
- 三句都完成或失败/取消时释放 Flow 和 token 队列。超过三句则每三个句段
  再开一批，不把全部长文 token 常驻。
- 20 ms 采样低于 800 MB 不记成功；Flow 初始化及复用前仍需至少 1200 MB
  可用内存。音频队列目标 2 秒、硬上限 4 秒；仍是句级播放。
- 统一报告记录 `pipelineMode=three-sentence-staged`、每批准备耗时和大小、
  Flow 创建/复用次数、完整 EOS、计算 RTF、生成墙钟 RTF、首块入队、断供和
  最低可用内存。默认三句应为一次 Flow 创建、两次复用。

## 验收

先冷启动，用默认三句文字、HiFT Low、4 线程各运行两次；分享一个统一报告。
这轮重点看总计算时间、首句首块入队和最低内存。三句 token 必须都取得 EOS，
音频必须完整可听，报告不得有保护失败或异常播放断供。与旧两句记录比较时
注意声音长度和手机热状态的差异。若首句等待明显增加，即使总体耗时下降，
也不能直接设成默认。通过三句后才扩大到多批长文。

PC 数值回归已通过：三句分别为 20/42/27 speech token，四条受控生命周期
路线的 12 段均正常 EOS，Mel 与 PCM 相对基线 L2 均为 0。此测试只验证固定
输入、模型生命周期与数值一致性，不替代手机的内存、RTF、声音和播放测试。
ACE-Step 工程与 17 个 CosyVoice 模型文件均不变。
